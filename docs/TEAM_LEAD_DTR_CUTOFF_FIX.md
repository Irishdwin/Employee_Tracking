# Team Lead DTR Cutoff Review HTTP 500 fix

Verified 2026-10-09 against the connected project.

1. **Failing endpoint:** `Api/TeamLead/get_dtr_cutoff_review.php?site_id=4` (optional `cutoff_ref=YYYY-MM-DD`), loaded by `loadDtrCutoffReview()` in `Html/TeamLead/team_lead_dashboard.html`.
2. **Actual cause:** Apache error.log records `Unworked holiday on 2026-10-05 requires Accounting review: verify attendance on the preceding scheduled workday 2026-10-02.` The production payroll helper correctly raised an eligibility-review exception. The list endpoint treated that employee-specific business condition as a fatal error for the entire roster. It also recomputed submitted DTRs before reading their frozen classification.
3. **Files changed:** `Api/TeamLead/get_dtr_cutoff_review.php`, `Api/TeamLead/submit_dtr.php` (remove internal error details only), `Html/TeamLead/team_lead_dashboard.html`; regression tests `Testing/Attendance/dtr_cutoff_review_test.php`, `Testing/Attendance/dtr_cutoff_ui_test.cjs` and their JSON results; this report.
4. **Database corrections:** none. No migrations, record repairs, or production payroll writes. Attendance PDO uses the same selected database as the existing mysqli connection.
5. **Loading:** catch only recognized payroll review conditions per employee, return `requires_review` and a readable reason, leave unverified aggregate totals null, preserve the full cutoff/roster and actual daily records. Other exceptions retain a logged HTTP 500 with a generic JSON message. Submitted rows use saved totals/classification without recomputation. Holiday badges use the existing employee/deployment-scoped holiday resolver. Invalid calendar dates return 422 rather than silently selecting another cutoff. Loading clears stale cutoff/selection; obsolete responses and site-loading errors cannot overwrite the newer selection. Review-blocked rows display the reason in both list and detail modal and cannot be selected.
6. **Multi-site verification:** read-only calls through the corrected endpoint for the affected Team Lead's authorized sites 4, 5, 6 and 7 all returned success with the default Type B Sep 26–Oct 10, 2026 cutoff. Site 4 returned five employees (two submitted, three requiring holiday review); site 6 returned a valid empty roster. Disposable HTTP tests verified branch employee isolation and unauthorized-site 403.
7. **Submission and locks:** existing server authorization, selected-site ownership, duplicate prevention and transaction rules are unchanged. Payroll review still blocks submission with 422. Saved submissions remain submitted and keep their recorded classification even if current attendance now triggers a review guard. Accounting submission, verification, computation, export review, finalization and frozen employee payslips passed all 13 scenarios. The shared payroll calculator and payroll formulas were not edited.
8. **Tests:** PHP syntax checks passed for both changed endpoints and the test runner. `dtr_cutoff_review_test.php`: 13 scenarios PASS, 24 guard checks PASS, production checksums unchanged, disposable database removed. Covers regular/holiday/approved overtime hours, review isolation, unknown totals, submitted snapshots, historical cutoff, empty cutoff, site authorization/isolation, duplicate submission and finalized payslips. `dtr_cutoff_ui_test.cjs`: 1366px and 390px PASS using the unchanged dashboard functions extracted from the actual page with controlled API responses; checks loading, stale response rejection, cutoff rendering, blocked/locked selection, eligible selection and empty state. All inline dashboard scripts parse successfully. These focused browser checks do not constitute a full retest of unrelated dashboard modules; those modules were not changed.
9. **Remaining data review:** Accounting must verify preceding-day attendance for affected employees before holiday valuation/submission. This is now visible in the UI rather than an HTTP 500. The fix does not assume eligibility or fabricate missing hours. Historical review continues the existing current-deployed-team roster policy; this change does not expand access to ended deployments.
