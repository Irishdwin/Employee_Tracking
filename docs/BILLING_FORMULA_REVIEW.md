# Billing formula export: implementation and outstanding financial review

Status: **partially implemented, not full SAMPLE.xlsx parity**. The request explicitly says to stop changing a specific formula when it conflicts with production payroll rules. Those conflicts have been left unchanged pending the two review questions presented in the chat. No payroll calculation rules or database schema were changed.

1. **Inspected flow/files.** `Html/Accounting/accounting_dashboard.html`, `Js/Accounting/accounting.js`, `Api/Accounting/get_payroll_runs.php`, `Api/Accounting/export_client_billing.php`, `Api/Accounting/Lib/client_billing_spreadsheet.php`, `Api/Helpers/client_billing_helper.php`, `Api/Helpers/employee_payroll_helper.php`, `Api/Helpers/billing_revision_helper.php`, `Api/Helpers/accounting_profile_helper.php`, `Api/Accounting/profile.php`, and the existing billing regression suites. The UI requests the existing XLSX endpoint; it resolves the selected run and verified employee roster/frozen membership, uses the production helpers, prepares a signed server snapshot, renders the template, writes XLSX, stores the historical file, and downloads it.

2. **Root cause.** The renderer loaded the correct template, cleared every employee cell, wrote some substitute formulas, then overwrote numerous calculation columns with numeric payroll values. Its final billing-override loop could overwrite formulas again. The XLSX writer preserves formulas; CSV and a values-only template reader were not involved. Whole-row `duplicateStyle()` also copied the first cell's style across columns, losing their distinct formatting.

3. **Actual workbook.** The provided file and `Templates/SAMPLE.xlsx` are byte-for-byte identical (SHA-256 `231d425ef115a2e3215586e57139dd4621160104eaf971f63cac393fd7c506b7`). The sheet is `JUNE 16-30 2026`; ten named employee rows occupy 6–15, row 16 is a separate blank exception with distinct formulas, row 17 contains totals, C23:C45 contains the summary, and B51 is the prepared-by name above B52 `PAYROLL IN-CHARGE`. Hidden columns include AC, AF, AG and AN. The source has no freeze pane. Native fonts, fills, borders, number formats, alignments, widths, heights, merges and landscape print settings were inspected through PhpSpreadsheet and worksheet XML.

4. **Strategy.** Continue loading the existing genuine client template. Restore compatible formulas from actual source cells with PhpSpreadsheet relative-reference translation. A restoration is accepted only if its rounded result equals the current authoritative amount; explicit confirmed billing overrides remain intact. This is a limited compatibility fix while conflicting formulas await review, not a replacement payroll engine.

5. **Production files modified in this task.** `Api/Accounting/Lib/client_billing_spreadsheet.php` (compatible formulas, special-row preservation, row resizing, column-specific styles, original panes); `Api/Helpers/client_billing_helper.php` (include the engine's existing late/undertime minute input in exported data); `Api/Helpers/billing_revision_helper.php` (capture actual calculated results from the trusted generated workbook for the signed import baseline). Existing test fixtures in `Testing/PayrollBilling/workflow_test.php` and `sunday_allowance_test.php` were updated to capture the same baseline as production and read formula results instead of formula text.

6. **New files.** `Testing/PayrollBilling/template_inspection.php`; `Testing/BillingFormulaExport/preview.mjs`, `capture_test.php`, `renderer_test.php`; this report. Local test workbooks and preview PNGs are in `Testing/BillingFormulaExport/`. They contain synthetic test data or the provided sample, and are not payroll release artifacts.

7. **Database.** No new migration, column or production data rewrite. The existing snapshot JSON now receives late minutes where freshly calculated. Regression suites create and remove isolated temporary databases; their profile edits and payroll revisions do not affect actual staff accounts.

8. **Employee formulas.** A uses the template sequence formula; G, I, K, M, P, AD and AM are restored from source when compatible with authoritative/revised data. Exact examples include `=F6*E6`, `=E6*1.25/8`, `=I6*J6`, `=E6/8/60*L6`, `=E6*5/12/2`, `=AB6` and `=AD6-AL6`. A mismatch keeps the existing authoritative value. Explicit imported overrides are preserved. Other financial calculation cells are not claimed to match SAMPLE.xlsx yet.

9. **Totals.** Preserve the actual source SUM columns, including its deliberately blank AQ total. Their span includes the ordinary rows and the preserved blank exception. Zero employees retain a blank styled ordinary row and formula totals. No hardcoded total amounts were introduced.

10. **Summary.** Inserting/deleting ordinary rows updates the existing summary references and moves the signature section naturally. Tests verify its first summary reference points to the resized total row and that no formulas contain `#REF!`. The client's existing summary/grand-total formulas remain present; full financial parity remains subject to the conflicts below.

11. **Variable rosters.** Tested 0, 1, 10, 11 and 17 employees. Additional ordinary rows copy each column's own style; existing rows retain their individual native styles. Original row 16 is always kept as an unassigned blank exception, with its distinct N, W, Y, Z, AD, AE, AJ, AP and AR formulas translated to its new position. It is never arbitrarily assigned to the eleventh employee. If that row represents a specific employee category, its business mapping still needs review.

12. **Allowance.** Production Sunday allowance remains supported and counted once in authoritative payroll. Its requested relocation into O is **not completed**: the existing H input includes Sunday premium plus Sunday allowance, O includes the separate regular allowance, and the importer uses that same mapping. Moving only the display cell would double-count/misinterpret subsequent revisions. This mapping must be resolved together with the conflicting N/AA/AB and H day-count usage, without changing the production engine.

13. **Prepared by.** The endpoint still retrieves the current authenticated Accounting user's name through the existing secure profile helper, writes it as literal text, and creates a new historical artifact. The isolated profile test saves Maria Santos, exports, renames that account to Pedro Garcia, exports again, verifies the new name, and confirms the old workbook still contains the old name. Formula-like names remain literal strings.

14. **Formatting.** The genuine template remains unmodified. Native per-column/per-row styles, ordinary and exception heights, column widths, hidden columns, merges and print settings are retained. The artificial E6 freeze pane has been removed because the actual template has none. Baseline and generated workbook previews were rendered for inspection; exact style comparisons are included in the renderer tests.

15. **End-to-end export.** Executed the actual export/import APIs through HTTP in the existing isolated billing test harness, using a two-employee site-specific test payroll run. The endpoint returned an XLSX; unchanged re-import, a one-employee revision, confirmation, idempotency, employee history, role/CSRF/IDOR controls and historical-download behavior passed. **An export of an existing live production run was not executed**, and no live Accounting account was renamed.

16. **Programmatic verification.** The trusted-template capture/save test passed 14 assertions. The renderer test passed 1,434 assertions across five roster sizes, covering translated formulas, style equality, the exception row, summary links and absence of broken references. The billing workflow suite passed 100 checks; the HTTP suite (including those workflow checks) passed 116. The allowance/profile/history suite passed 44 checks. Uploaded formulas remain untrusted and are rejected when changed; only server-generated workbooks are calculated for baseline capture. Legacy stored baseline fallback remains supported.

17. **Native recalculation.** A hidden Excel instance opened a disposable template test copy, recalculated, changed E6 from 700 to 800, and recalculated G6 from 1,400 to 1,600 while retaining `=F6*E6`. A renderer-generated test export also recalculated G6 from 1,000 to 1,200 after E6 changed from 500 to 600. Both copies were saved separately and the test Excel instances closed. This proves restored cells recalculate; it does **not** prove full client grand-total recalculation while conflicting cells remain numeric.

18. **Unresolved conflicts and completion limits.** Full parity is not complete. The specific conflicting rules have not been silently changed:

    - H is a peso amount in production but is used as a day count in client AT/AU formulas. Sunday allowance must move to O with a safe import mapping, not a cosmetic relocation.
    - N in the client adds basic/ordinary overtime and subtracts lates; production also includes Sunday amounts and other overtime components.
    - P is added to client Additional Total through AA; production exposes SIL accrual separately and does not include it in gross pay. Historical/confirmed overrides may also differ from rate-based accrual.
    - S simplifies to `E/8*R`; production regular-holiday compensation includes full statutory holiday rates/guarantees. U fixes the multiplier at 2.6 while production supports rest days/double holidays. W is only a 30% premium in ordinary employee rows; production reports full applicable holiday pay. Y/Z support different effective rates in the current exporter. These must not be silently reduced to the sample's fixed rates.
    - AJ aggregates AG+AH+AI in the client but currently holds Pag-IBIG EE directly. AL sums only AE+AF in the client while production includes the employee's SSS, PhilHealth, Pag-IBIG and other deductions.
    - Client AQ/AR link to EE contribution cells, and AS excludes AQ; production uses the actual ER contribution fields and includes all ER dues.
    - AT is based on rate and F+H days in the client; production accrual is based on authoritative earnings. AU uses fixed 36.50 per day while production uses the run's overhead percentage. AW excludes row-level VAT, while production invoices include it. The client summary applies its own VAT/withholding structure.
    - The client permits formula-driven gross/additional/net results that can consequently differ from finalized engine payroll and signed imported revisions. Choosing exact client-report formulas requires an explicit decision about those reporting differences and import semantics.

The pending review question is whether to reproduce SAMPLE.xlsx exactly as a client billing report while keeping engine payroll/payslips authoritative, or retain production calculations for the conflicting cells. The second question is whether the blank special row stays unassigned or belongs to an identified employee/category. The safe changes above are implemented and tested without waiting for a generic “PROCEED.”
