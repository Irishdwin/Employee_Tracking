# ONAZUL HRIS data flow diagrams

System: **Web-Based Employee Tracking, Deployment, and Payroll Management System for Onazul Manpower Services**.

Prepared 8 October 2026 from the current Employee_Tracking working tree, including uncommitted implementation changes, and the live `onazul_hris_db` schema. These diagrams describe logical business information flows, not database keys or server architecture. No application source was changed.

## Reading and editing

The default viewer now opens `DFD_Standard_Level_1.svg`, a concise standard Gane & Sarson presentation. It consolidates the original fourteen processes into eight business processes, uses repeated store references for shared inputs, and groups participating external roles explicitly. `standard_model.json` records the process grouping; `build_standard.cjs` rebuilds its editable SVG and Mermaid source. The standard sheet's D1–D8 are its own logical group identifiers: accounts; recruitment; staffing/deployment; employees/separation; work time (including overtime, existing leave and add-back evidence); payroll/billing; communications; audit/reference. Document and evidence files belong to the associated business record groups at this level. Consult the original detailed sheets for endpoint evidence, individual role permissions, Google/email interfaces and finer store breakdown. Numbering on this consolidated sheet differs from the original detailed decomposition.

Start with `DFD_Level_0_Context.svg`, then `DFD_Level_1.svg`. The complete Level 1 is a large landscape diagram; view at native size with zoom. Use the three focused detail sheets for presentation: recruitment, attendance and payroll. These repeat the original process numbers and show boundary processes; they are extracts, not additional Level 2 decompositions. `DFD_Level_2_Payroll.svg` decomposes process 9.0 specifically.

Each of the six diagrams has Mermaid `.mmd`, Graphviz `.dot` and rendered `.svg` files. Both source formats are editable. SVGs are rendered from DOT using the same nodes and directed labeled edges as Mermaid. All rendered diagrams follow **Gane & Sarson**, the second column of the user's supplied “Data Flow Diagram Methods & Symbols” reference: external entities are rectangles, processes are rounded rectangles, stores have left/top/bottom borders with the right side open, and flows are labeled single-headed arrows. The symbol families are not mixed with Yourdon & De Marco, SSADM or Unified notation. Green strokes and restrained fills echo the reference. Mermaid uses rounded processes but double-bordered rectangles for stores as a notation approximation; use the editable DOT and its SVG for exact Gane & Sarson symbols. Arrows carry information names; they do not assert temporal sequencing.

`model.json` is the full logical model. `build_dfd.cjs` rebuilds it and the diagrams with the available bundled `@viz-js/viz` renderer. Set `CODEX_NODE_MODULES` to another node_modules directory containing that package if moving the project. Run `node docs/dfd/build_dfd.cjs`. `verification.json` records boundary balancing and counts. `index.html` provides a local viewing and print entry point.

## External entities and context boundary

The live roles table and backend guards confirm Admin, HR, Applicant, Employee, TeamLead and Accounting. The diagram labels the last two Team Lead / Site Supervisor and Accounting Staff for readers. “Portal Users” repeats these same six entities to factor shared authentication, notification and Messenger arrows; it is not a seventh role or an unrestricted user permission.

Google Identity Service supplies public signing keys used to validate the Google ID token submitted by the user. It is not shown creating local roles or granting access. Email Delivery Service receives verification and recovery messages. External service code exists; provider availability and configured production delivery were not exercised.

There is no separate Client role in the live roles table and no independently implemented client portal in the scanned pages and guards. Team Leads submit company job orders and record endorsed-applicant client decisions. Accounting exports billing and records client approval/revision/release information. Client Company is therefore not drawn as an additional direct portal entity. Off-system client exchange is described here rather than inventing a client-to-API connection.

Context arrows summarize Level 1 external flows per entity and direction. `context_balance.json` maps each concise Context label to its exact Level 1 boundary labels; the build verifies full directional coverage. This preserves both directions without asserting that every role may use every module.

- **D1 Accounts and Security:** `users`, `roles`, `employee_password_history`, `teamlead_personal_profiles`; security/profile values also live in the account record. PHP sessions are transient authentication state, not a separate invented database table.
- **D2 Applicants and Applications:** `applicants`, `applicant_profiles`, `applicantdocuments`, `applicant_uploaded_docs`, `job_applications`, `application_endorsement_attempts`. Document metadata here references D15 content.
- **D3 Employees and Separation:** `employee`, `employmentcontract`, `resignationrequest`, `clearance_items`. Contract upload paths/remarks also occur in the recruitment workflow; not every uploaded contract is assumed to create an employmentcontract row.
- **D4 Clients and Agreements:** `clientcompany`, `serviceagreement`, `industry_lookup`.
- **D5 Job Orders and Classifications:** `joborder`, `job_order_requests`, `job_order_details`, `joborderpositions`, `jobrequirements`, `job_categories`, `job_classifications`, `job_sub_classifications`.
- **D6 Sites and Deployments:** `deployment_sites`, `deployment`, including worksite/geofence context persisted by the site helpers.
- **D7 Schedules and Holidays:** `team_schedule_entries`, `work_schedule_lookup`, `holidays`, `holiday_deployment_sites`. Fixed schedules are also stored in `deployment` (D6).
- **D8 Attendance and DTR:** `attendance`, `daily_time_records`, `dtr_submissions`. Parallel attendance/DTR representations are grouped logically, not portrayed as two independent employee clocking systems.
- **D9 Overtime and Existing Leave:** `overtime`, `leaves`. Only overtime has the demonstrated self-service request/response workflow. Existing approved leave is read by attendance/payroll context; no leave write/approval arrow is asserted.
- **D10 Payroll, Billing and Status History:** `payroll`, `payroll_runs`, `payroll_run_members`, `payroll_billing_exports`, `payroll_billing_revisions`, `payroll_billing_adjustment_sources`, `payroll_adjustments`, `payroll_audit_log`, `payroll_status_history`, `payroll_group_status_history`, `payroll_run_status_history`, and compensation-context tables `cashadvance`, `cashadvancededuction`, `bonus`, `deductions`, `salary_rates`. These are logical grouping members, not claims that every current calculation reads every legacy table. `payslip` exists in schema, but current employee payslip details are read from finalized `payroll`/run snapshots; no unsupported payslip-row creation arrow is shown.
- **D11 Notifications:** `notifications`.
- **D12 Messenger:** `chat_threads`, `chat_thread_participants`, `chat_messages`, `chat_thread_reads`. Some presence/read fields reside in existing account/chat records.
- **D13 Audit and Configuration:** `system_logs`, `systemsettings`, `sss_rates_config`, `gov_percentage_rates`; lookup/status/address reference tables support processes without individual diagram nodes.
- **D14 Add Back Requests and Evidence:** `add_back_requests`, `add_back_evidence`.
- **D15 Uploaded Documents and Evidence Files:** actual `uploads` filesystem content referenced by application metadata: applicant/employee documents, contracts, attendance evidence, quitclaim, billing/proof attachments. This is a file data store, not a claimed SQL table. Access-controlled download endpoints mediate reads.

## Critical flow interpretation

Recruitment moves from application and HR review to endorsement, Team Lead-recorded client decision, contract and hiring. Hiring writes employee identity and elevates the local account role. Job orders carry multiple position/site details, not just one staffing count.

Team Leads are scoped using assigned `deployment_sites`, not a universal one-company/one-site assumption. The schedule helper authorizes a deployment by the site's TeamLeadID. DTR submission locks the chosen site and batches by site/cutoff. Payroll computation rejects a batch spanning ambiguous company/site contexts. Legacy company-level Team Lead association remains in some recruitment paths; the diagrams do not claim that all modules use only site-level scope.

Attendance consumes effective shifts, geofence and deployment context; it persists validated clock and evidence information. Approved overtime and existing approved leave contribute to attendance/payroll calculations according to their actual helper rules. Employee leave UI explicitly directs filing to HR via Messenger. There is no invented self-service leave submission/approval process in these diagrams.

The current regular payroll sequence is: submitted DTR → Accounting verification → site-scoped computation preview → persisted billing export → human export review → guarded finalization → finalized payroll/run snapshots → employee payslip/history. Finalization checks a fresh export after computation, exact roster/site/DTR membership and verified DTRs. It publishes the payslip independently of release status.

Client workbook revisions are previewed and explicitly confirmed by Accounting; revision code requires matching finalized payroll and frozen run members, then writes audited adjustments and updates totals. These are not unverified spreadsheet values flowing directly into employee history.

“For Client Approval,” “Returned for Revision,” “Client Approved,” “Payroll Released,” “On Hold,” and “Needs Correction” are manually recorded status values with optional remarks/proof, not evidence of a bank transfer. Code does not enforce payment/funding confirmation before finalization or a mandatory sequence between all these status values. No bank, payment processor, automated funding receipt, or direct client approval API is included.

## Verification, scope and limitations

Read-only live MySQL inspection confirmed 74 tables and the six role names. Current backend SQL, permission guards, frontend page references and fetch calls were traced across the modules above. The SQL dump is older than the current live schema; it was supplemented by the live table inventory, migrations and current helper SQL rather than treated as the sole authority.

No production transactions, hiring, attendance, payroll changes or provider messages were performed for this documentation task. This is implementation/schema verification, not end-to-end certification of every runtime path. Google/email provider configuration, real client off-system exchange and actual payment execution cannot be verified from this run. External services are code-supported interfaces whose operational configuration may vary.

Existing leave rows and some legacy compensation tables are schema-supported context, not proof of complete CRUD workflows. No planned features are mixed into the primary DFD and no future diagram is included. Authentication/read notifications/Messenger entity factoring and logical grouping of tables/files are diagramming choices, not unverified business assumptions.

The automated model check validates referenced node IDs and Context/Level 1 boundary-label coverage. All six DOT diagrams render successfully to SVG; browser render checks and previews are recorded separately. SVG preserves full-resolution labels. The complete Level 1 is intended for zoomed analysis; the focused sheets and Level 2 payroll are the readable presentation views.
