# Attendance testing visibility fix

Verified 2026-10-09 in the connected Employee_Tracking project.

1. **Confirmed root cause:** The screenshot's October 6–9 records already existed in both `attendance` and `daily_time_records`, with matching EmployeeID, dates/times and EvidenceDeploymentID. Read-only calls to the Employee and authorized Team Lead attendance APIs returned all four records. This was not a separate database, mock-data, or failed-insert problem. The Employee synchronizer dispatched `employee-attendance-updated` on `window`, while the calendar listened on `document`, so refresh events missed the calendar. A second listener would duplicate delivery after correcting the target; it was removed. The calendar and Team Lead monitoring table also used raw clock state (`Clocked Out`) rather than the computed attendance status (`Present`/`Late`). Historical month changes did not scope the employee's periodically refreshed logs table. These confirmed frontend defects are corrected; the screenshot alone cannot establish which employee account was open in another browser.
2. **Testing storage:** `Testing/Attendance/Api/save_attendance.php`, using the same production mysqli connection, atomically writes `attendance` and `daily_time_records`, records the actual dated deployment in existing `EvidenceDeploymentID`, and writes an Attendance Testing audit entry. This dual-write was already correct and was not replaced. No GPS coordinates or photos were fabricated.
3. **Employee reader:** `Api/Employee/get_employee_attendance.php`; session UsersID resolves the employee by the existing account/email relationship. Explicit start/end ranges retain the existing 62-day limit. The response now includes late minutes and the requested range. The synchronizer sends fresh, noncached requests, delivers one event to document (bubbling to window), and uses the calendar's selected range for subsequent polling. Range refresh removes old map entries before applying current records, so deleted records do not remain on the calendar. Errors are visible rather than silently ignored.
4. **Team Lead reader:** `Api/TeamLead/get_employee_attendance_logs.php`; existing server-side current-site ownership remains mandatory. The monitoring modal includes the selected site, supports attendance-month selection and Refresh, rejects stale modal responses, and renders computed statuses. A requested month now filters history records, not just calendar metadata. Invalid months return 422. Both readers use PDO for the same database selected by their mysqli connection and return no-store headers.
